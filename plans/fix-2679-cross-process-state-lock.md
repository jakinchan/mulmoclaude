# fix(calendar): 状態ファイルの read-modify-write をプロセス間で排他する (#2679)

## Request

`.sync-state.json` と `.push-state.json` はどちらもファイル全体の read-modify-write。
同一プロセス内は write queue が順序を付けるが、**プロセス間には何も無い**ので、同じワークスペースを
指す2ホストが同じスナップショットを読み、後の書き込みが前のエントリを落とす（lost update）。

## 調査で分かっていること（issue のコメントに記載済み）

- **データは壊れない。** merge の構造上、lost update は必ず「古い値が残る」方向にしか倒れず、
  `conflictingFields` は shadow が古いほど conflict を**過剰に**出す
- 実害は **sticky な偽陽性 conflict**（既に Google と一致しているのに、解決されるまで conflict を
  報告し続ける）と、**重複したフルウォーク / API 消費**
- Google 側への書き込みは client-set event id + 409 adopt と etag `If-Match` + 412 で既に守られている

## 方針 — ロックの粒度を「同期全体」ではなく「状態ファイルの書き換え」にする

issue 本文は `withCalendarLock` の内側（＝同期全体）にロックを敷く案だったが、**閉じるべきは
read→write を跨いだ排他だけ**で、その保持時間は**ミリ秒**。粒度を下げると難所がまとめて消える:

| 同期全体に敷く場合 | 状態ファイルの書き換えに敷く場合 |
|---|---|
| 手動経路が待たされる → **busy という新しい結果**（outcome 型 / ルート / UI） | ms 待てば取れるので **busy 不要** |
| 保持がフルウォークの数分に及ぶ → **heartbeat が必須**、TTL の見積もりが難所 | 保持が ms なので **TTL 10秒で足り、heartbeat 不要** |
| クラッシュしたホルダーが分単位でブロック | 最大10秒 |

代償は「2ホストが同じカレンダーを同時に walk する無駄」が残ること。#2678 の soft-dedup が
スケジュール経路で既に減らしており、**データは壊れない**ので、実害に対して桁違いに安いこちらを採る。

## 設計

`calendarStateLock.ts` を新設。`<state file>.lock` を `O_EXCL`（Node の `wx`）で作る。

- **ロックファイルの中身**は `{ holder, at }`。`holder` は `randomUUID()`。秘密ではなく、
  「解放するとき、自分のロックだけを消す」ためだけに一意であればよい
- **解放**は holder が一致するときだけ unlink。steal の後に別のホストが取ったロックを消さないため
- **stale 回収**は TTL 10秒。年齢を見る前に読んだ holder を、unlink の直前に読み直して一致を確認する
  （更新したばかりのホルダーを追い出さない）。それでも2プロセスが同じ死体を同時に片付ける競合は
  残るが、負けたときの代償は lost update 1回 ── **本 PR が減らしているものであって、新しい失敗ではない**
- **読めないロックファイルは即座に回収する。** `release` は holder が一致するファイルしか消さないので、
  壊れたロックは**誰も解放できない**。待っても無駄で、以降のすべての mutation が待ち切ってから
  unlocked に落ちるコストを払うことになる（これは自分で書いたテストが**タイムアウトを消化して
  pass していた**ことで気付いた）
- **fail open**。ロックが作れない（read-only マウント、ディレクトリ不在、ディスク枯渇）ときも同期は
  続ける。ロックは競合を減らすものであって、正しく同期するための前提条件ではない（#2678 と同じ姿勢）

`writeQueue` は**残す**。ロックは1回の read-modify-write 単位なので、同一プロセスの2つの mutation は
queue が無いと依然として交錯する。**両方要る。**

## 限界（仕様として明記する）

`O_EXCL` はローカル FS と NFSv3+ では atomic だが、**Dropbox / iCloud / Google Drive のような
同期フォルダにワークスペースを置いた構成では排他にならない** ── ファイルは事後に複製されるので、
両ホストが「自分が持っている」と信じる。この構成は #2678 / #2679 のどの手段でも守れない。

## スコープ外

- **同期実行そのものの排他**（重複フルウォークの防止）。busy UX と heartbeat を要求する別物で、
  データ損失ではなく API 消費の問題。必要になったら別 issue
- **`withCalendarLock`（プロセス内キュー）の変更**。触っていない

## テスト

`test/services/google/test_calendarStateLock.ts`。**実際の一時ディレクトリに対して**実行する ──
仕組みそのものが FS の `O_EXCL` なので、モックしても何も検証できない。

- 完了後にロックファイルが消えること／mutation の戻り値が返ること／throw しても解放されること
- **同一ファイルの2つの mutation が直列化されること**（このファイルの存在理由そのもの）
- 生きたロックが空かないとき、待ち切って **unlocked で続行**し、他人のロックは消さないこと
- TTL を過ぎた沈黙したホルダーのロックを回収すること
- **読めないロックファイルを、待たずに回収すること**
- 待っている間に置き換わったロックを消さないこと
