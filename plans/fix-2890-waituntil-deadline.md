# watcher テストの待機予算を締め切り方式にする (#2890)

## 何を直すか

`test/workspace/collections/test_watcher.ts` の `waitUntil` が「200回 × 5msスリープ」の
**試行回数**予算だったのを、**締め切り時刻**（10秒）に変える。

## issue の提案（計測プログラム）を採らない理由

issue は「実測 → 分布を見て決める」を求めているが、観測は1回だけで、しかもキャッシュキーを
意図的に変えた run（`build:packages` が走ってジョブ全体が重い）という特殊条件。同じ run の 22.x は
緑、再実行も緑。この1件のために「計測を仕込む → また落ちるのを待つ → 決める」を回すのは見合わない。

issue の「数字を上げるな」という戒めは、**観測された最悪値の近くにチューニングする**ことへの警告
として正しい。10秒は桁違いに余裕があるので性質が違う —— listener が動かなければアサーションは
やはり落ちる。壊れているときに失敗するまでが延びるだけで、バグは隠れない。

## issue の見立てのずれ（実測で確認）

「Windows は1試行が重いから予算が足りない」は逆。予算が `200回 × (5ms + done() の実行時間)` である
以上、**done() が重いほど壁時計では長く待つ**。使い捨てハーネスで新旧を並走させて確認した:

| ケース | 旧（200回） | 新（10秒締切） |
| --- | --- | --- |
| 常に false（安いチェック） | **1,164ms で失敗** | 10,004ms で失敗 |
| 常に false（1回10ms のチェック） | **3,310ms で失敗** | 10,000ms で失敗 |
| 即 true | 0ms で成功 | 0ms で成功 |
| 2秒後に true（今回の flake の形） | **1,124ms で失敗** | **2,001ms で成功** |

同じ「200回」が、チェックの重さで 1.1秒にも 3.3秒にもなる —— これが移植性の無さの正体。
そして「壊れていれば新しい実装でも失敗する」ことも同じ表で示されている（1行目・2行目）。

## やらないこと

- 計測ログの常時出力（成功のたびに4テスト分が CI ログに出るのは純粋なノイズ）
- ポーリングをやめて確定的な signal を待つ設計変更（根本策ではあるが、notifier engine 側に
  購読口を足す話になり、1回の flake に対して過大）

失敗時のメッセージには経過msを載せた。次に落ちたときは「予算切れ」なのか「本当に動いていない」
のかが、追加の計測なしにログから読める。
