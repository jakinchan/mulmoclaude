# feat(#2616): アイコンから起動したサーバを UI から終了する

アイコンランチャー（#2613 / PR #2615）はサーバを detach して spawn する。
ランチャー自身は即座に終了し、サーバだけが残る — 「アイコンをクリックしたら
数十秒後にアプリが開く」ために必要な設計だった。

その結果、**止める手段が `kill $(lsof -ti:3001)` しか無くなった**。
ターミナルを開かない人のために作った入口が、ターミナルなしでは止められない
アプリを生んでいる。CHANGELOG にも「唯一残る既知の穴」と書いてある。

## issue の検討事項に対する決定

| 論点 | 決定 | 理由 |
|---|---|---|
| 置き場所 | **設定モーダル**の最下段に専用グループ | ヘッダは常用アイコンが 10 個並んでいて、その隣に「終了」を置くのは誤クリックを誘う。終了は意図的な操作であるべきなので、2 クリック + 確認を挟む位置に置く |
| 確認 | 出す。8 言語 | 押し間違いの取り返しがつかない（再起動はアイコンをもう一度押す必要がある） |
| 停止後の画面 | **先に画面を切り替えてから落とす** | サーバが死んだ後のページ遷移はできない。サーバは 200 を返してから遅延して停止し、クライアントは 200 を受けた時点で終了画面に差し替える |
| リモート（スマホ）から叩けるか | **叩けない。追加のチェックも要らない** | サーバは `127.0.0.1` にしか bind していない（`server/index.ts` の `app.listen(port, "127.0.0.1")`）ので、HTTP 経路は構造的にローカル専用。RemoteHost は Firestore のコマンドチャネルで**別のハンドラ表**を持つため、そこに shutdown を足さない限り到達しない。足さない |
| 実行中のエージェント処理 | 確認文で「実行中の処理は中断されます」と述べた上で、確認したら止める | 「実行中か」を判定して分岐すると UI とセッション状態の結合が増えるうえ、判定が外れたときに黙って嘘をつく。常に真である一文を出すほうが正直で壊れない |

## 実装の芯: 停止ロジックを二重に持たない

`server/index.ts` には既に `gracefulShutdown(signal)` がある（shutdown hooks を
回して、トークンファイルを消して `process.exit(0)`）。SIGINT / SIGTERM から
呼ばれている。

**新しい停止経路を書かない。** ルートは自分自身に SIGTERM を送るだけにする:

```js
process.kill(process.pid, "SIGTERM");
```

これで停止手順は 1 つのまま。`gracefulShutdown` は `isShuttingDown` で多重実行を
防いでいるので、連打しても安全。

## 順序（ここを間違えると「押しても何も起きない」に見える）

1. クライアントが `POST /api/shutdown`
2. サーバは **200 を先に返す**
3. サーバは短い遅延のあと SIGTERM を自分に送る（遅延がないとレスポンスが
   ブラウザに届く前にソケットが切れる）
4. クライアントは 200 を受けた時点で終了画面に差し替える

## テスト

- ルートが **200 を先に返し**、レスポンス後に停止をスケジュールすること（`process.kill` は注入して差し替え、テストで本当に死なないように）
- 遅延が 0 でないこと（0 だとレスポンスが届かないことがある）
- 多重 POST で `process.kill` が複数回呼ばれても停止手順は 1 回であること（`gracefulShutdown` 側の保証を壊していないこと）
- 終了画面の文言が 8 言語そろっていること（ロックステップのテストが既にある）

## スコープ外

トレイ常駐 / 自動起動（#2613 と同じ）。RemoteHost からの停止（上記の理由で意図的に非対応）。
